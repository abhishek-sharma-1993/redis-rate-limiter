A rate limiter that refuses to take your API down

How I built a distributed token-bucket limiter on Redis and Lua for Spring Boot. It stays correct across every pod, costs one network round trip per check, and keeps enforcing limits even when Redis is gone.

    The short version

    • Token bucket, because burst size and steady rate are two separate, easy-to-explain knobs.
    • One Lua script per check makes read-refill-consume atomic in Redis, so two pods can never spend the same token.
    • Redis's clock, not the pods' clocks, decides how many tokens have refilled.
    • A deny cache, a circuit breaker and a local fallback mean a sick Redis costs the API almost nothing.
    • It ships as a Spring Boot starter: add one dependency and one annotation.

    Why rate limit at all

    Every public API eventually meets a client that sends more than you planned for. Sometimes it is an attacker. More often it is a well-meaning batch job with a retry loop.

    A rate limiter is the bouncer at the door. It protects the databases and downstream services behind your API, it keeps one noisy tenant from starving everyone else, and it puts a ceiling on what a runaway client can cost you.

    The hard part is not the algorithm. It is doing this across many pods, on every single request, without adding latency, and without turning the limiter itself into the thing that takes production down. That last requirement shaped almost every decision below.

    Picking the algorithm

    There are five classic options. They differ in how they treat bursts and how much state they keep per caller.

    AlgorithmBurstsState per keyCatch
    Fixed window counterUp to 2× at window edges1 counterA client can spend a full window at 0:59 and again at 1:00.
    Sliding window logExactEvery timestampMemory grows with traffic.
    Sliding window counterApproximate2 countersCheap, but an estimate.
    Leaky bucketSmoothed awayQueue or 1 valueGreat for shaping, but adds delay instead of a fast no.
    Token bucketExplicit: capacity2 numbersBurst and steady rate are separate knobs anyone can reason about.

    Token bucket is also what the big public APIs use. Stripe describes a token bucket per user, backed by Redis, and AWS documents that API Gateway throttles with a token bucket, where "burst" is the bucket size and "rate" is the refill speed.

    The model is simple: a bucket holds up to capacity tokens and refills at rate tokens per second. Each request takes one token (or more, for expensive calls). No token, no entry. Play with the bucket at the top of the page to feel it: fire a burst of 15 into a full bucket and 10 get through; after that, the refill rate decides.

    The race that breaks naive limiters

    The first version most of us write reads the token count, does the math in Java, and writes it back. On one server that works. On two pods it quietly fails.

    You could fix this with WATCH/MULTI/EXEC, but optimistic locking retries pile up on exactly the keys that matter most: the hot ones. A distributed lock adds two more round trips and its own failure modes.

    A Lua script solves it in one move. Redis treats a script like a single command and runs it to completion before anything else, so read, refill and consume happen together. I verified this with 2,000 concurrent requests against a 1,000-token bucket: exactly 1,000 were admitted.

    The Lua script

    This is the whole algorithm. It runs inside Redis, it is O(1), and the client sends only the script's 40-character SHA1 hash via EVALSHA, not the script itself.

    -- KEYS[1] = bucket key, ARGV = capacity, refill rate (tokens/s), permits
local capacity  = tonumber(ARGV[1])
local rate      = tonumber(ARGV[2])
local requested = tonumber(ARGV[3])

-- One clock for every pod: Redis's own
local t   = redis.call('TIME')
local now = tonumber(t[1]) * 1000000 + tonumber(t[2])   -- microseconds

local state  = redis.call('HMGET', KEYS[1], 't', 'ts')
local tokens = tonumber(state[1])
local ts     = tonumber(state[2])
if tokens == nil or ts == nil then tokens = capacity; ts = now end  -- new bucket starts full

-- Refill for the time that passed, never above capacity
local elapsed = math.max(0, now - ts)
tokens = math.min(capacity, tokens + (elapsed * rate) / 1000000)

if requested <= tokens then
  tokens = tokens - requested
  redis.call('HSET', KEYS[1], 't', tokens, 'ts', now)
  redis.call('PEXPIRE', KEYS[1], math.ceil((capacity * 1000) / rate) + 1000)
  return { '1', tostring(math.floor(tokens)), '0' }          -- allowed
elseif requested > capacity then
  return { '0', tostring(math.floor(tokens)), '-1' }         -- can never fit
else                                                       -- denied: no write at all
  return { '0', tostring(math.floor(tokens)),
           tostring(math.ceil(((requested - tokens) * 1000) / rate)) }  -- retry after, ms
end

    The repository version is the same logic with a single return statement. Each reply carries three things the caller needs: allowed or not, tokens left, and how long to wait.

    Four details that matter in production

    Each is a small decision in the script, and each removes a whole class of production bugs.

    Clock

    Redis decides what time it is

    If pods used their own clocks, a pod running 2 seconds fast would mint free tokens. Using TIME inside the script gives every pod the same "now". This is safe on replicas because, since Redis 5, scripts replicate their resulting writes rather than being re-run.

    Writes

    A denial writes nothing

    The stored tokens and timestamp project to exactly the same future whether or not we save the refill. So a rejected request skips HSET entirely. A flood of abusive traffic causes zero writes and zero replication traffic.

    Memory

    Buckets clean themselves up

    Each key expires after "time to refill completely, plus one second". An expired bucket behaves exactly like a full one, so expiry never changes a decision. One bucket is a small hash of about 100 bytes.

    Sharding

    One key per bucket

    The script touches a single key, so it works on Redis Cluster with no hash-tag tricks. Buckets spread evenly over all 16,384 hash slots, and throughput grows as you add shards.

    Architecture

    The limiter is not a separate service. It is a library embedded in every app pod, so there is no extra network hop and nothing new to deploy or scale. Redis is the only shared component, and it runs replicated.

    What each piece does

    • Entry points. Put @RateLimit(capacity = 10, refillPerSecond = 5) on a controller method, or inject the RateLimiter bean anywhere: Kafka consumers, gRPC handlers, scheduled jobs.
    • Key resolver. Decides who is being limited. key = "#pathVars['merchantId']" gives each merchant its own bucket. Expressions run in a restricted SpEL context that cannot load classes or touch beans.
    • Engine. Coordinates every check in a fixed order, cheapest first, and wraps everything so the caller always gets a decision, never an exception.
    • Lettuce. Lettuce connections are thread-safe and multiplex many in-flight commands over one socket, which suits short commands like EVALSHA better than a connection pool.

    Using it takes one dependency and one annotation:

    @RateLimit(name = "merchant-orders", capacity = 100, refillPerSecond = 50,
           key = "#pathVars['merchantId']")
@GetMapping("/api/merchants/{merchantId}/orders")
public Orders orders(@PathVariable String merchantId) { ... }

// or anywhere else
RateLimitDecision d = rateLimiter.tryAcquire("export:" + userId, BucketConfig.perMinute(30));

    Life of a request

    Every check walks the same path. The cheap local answers come first, and the network is the last resort, not the default.

    When Redis dies

    A rate limiter that fails closed takes your API down with it. One that waits on a dead Redis adds a timeout to every request. Both are outages you caused.

    So the library has three layers of defence, from "Redis is fine" to "Redis is gone":

    • Replication. Redis Cluster or Sentinel promotes a replica when a primary fails. Many incidents end here.
    • Tight timeouts. 50 ms per command and 200 ms to connect. A slow Redis can cost a request at most that, and only until the circuit breaker trips.
    • A circuit breaker that stops calling Redis entirely once it is clearly unhealthy.

    While the circuit is open, or when a call errors out, a configurable policy decides what happens:

    PolicyBehaviourGood for
    LOCAL (default)Each pod enforces ratio × limit with an in-memory bucket. With 3 pods, a ratio of about 0.34 keeps the fleet near the global limit.Most APIs. Still protected, still up.
    ALLOWLet everything through.Read-heavy endpoints where availability wins.
    DENYReject everything.Login, OTP and payment endpoints, where letting abuse through is worse than refusing service.

    The honest trade-off: during an outage the LOCAL limit is approximate, because pods are not coordinating. If the pod count changes mid-outage, the fleet total drifts. I chose an API that stays up and roughly protected over one that is perfectly accurate and down.

    The deny cache: answering without asking

    This is my favourite piece, because it is both a big win and provably safe.

    When Redis says "caller X needs another 800 ms before one token exists", that is a hard lower bound. Tokens only arrive at the refill rate, and other pods can only take tokens, never add them. So for the next 800 ms, any request from X for at least that many permits is guaranteed to be rejected. The pod can say no from memory.

    Two details keep it correct. A smaller request still goes to Redis, because it might fit where the larger one did not. And entries expire on their own, with the cache bounded in size. The guarantee holds as long as the bucket's configuration does not change during that short window.

    Scaling out

    Redis Cluster splits keys into 16,384 hash slots by CRC16(key) mod 16384 and spreads the slots over primaries. Because each bucket is exactly one key, buckets scatter evenly. Even neighbouring IDs land on different shards:

    Back-of-the-envelope capacity

    • Memory: about 100 bytes per active bucket, so 10 million active callers fit in roughly 1 GB.
    • Throughput: each check is one short O(1) script. Total capacity grows roughly linearly with the number of primaries, and the deny cache removes most abusive traffic before it reaches Redis.
    • The real limit is a hot key. One tenant at enormous traffic is pinned to one shard. The deny cache absorbs its rejected requests; for its allowed ones, the next steps are token leasing (pods pre-fetch small batches of tokens) or splitting that tenant into several sub-buckets.

    Benchmarks

    I benchmarked the Lua script on its own with redis-benchmark, 50 concurrent clients, on a deliberately small machine: a single vCPU shared by Redis and the load generator. Treat these as a floor, not a ceiling.

    What the numbers say: the script costs roughly 2.5 to 3 times a plain GET, which is the price of an atomic read-refill-write. p99 stays under 1.5 ms even with all 50 clients fighting over a single key. And the denied path is measurably cheaper than the allowed one, because a denial skips the write and its replication entirely.

    Correctness matters more than speed, so the integration suite also fires 3,200 requests from 64 threads across 4 simulated pods at one 500-token bucket, and asserts that exactly 500 are admitted.

    Trade-offs I accepted

    • One network hop per allowed request. Pre-fetching tokens locally would remove it but trades precision for speed. I kept exactness and put leasing on the roadmap.
    • Brief over-admission after a failover. Redis replication is asynchronous, so a promoted replica may have missed the last few writes and think buckets are fuller than they are. For a rate limiter, letting a few extra requests through is the right side to err on.
    • Approximate limits while Redis is down. Covered above: available and roughly protected beats exact and offline.
    • Library, not a service. No extra hop and no new deployment, but every service must pull the dependency. A gateway is still the right place for coarse edge limits; this handles fine-grained, business-aware ones, including non-HTTP traffic.

    Interview cheat sheet

    If you are preparing for a system design round, these are the follow-ups this design invites. Tap to reveal.

    Why not do the token math in Java and store the result?
    Read-compute-write from two pods interleaves, so both can spend the same token. Making it atomic needs either optimistic locking with retries, a lock with extra round trips, or a server-side script. The script is one round trip and cannot be interleaved.
    What if a pod's clock is wrong, or Redis's clock jumps back?
    Pod clocks are never used; Redis TIME is the single source of time. If Redis's clock moves backwards, elapsed time is clamped to zero, so no tokens are minted.
    Is TIME inside a script safe with replication?
    Yes. Since Redis 5, scripts are replicated by their effects (the resulting writes) by default, and Redis 7 removed verbatim script replication altogether. Replicas apply the same values instead of re-running the script.
    How do you enforce two limits at once, like 10 per second and 1,000 per day?
    Check two buckets. To make it all-or-nothing, extend the script to take both keys and only consume when both have tokens. On Redis Cluster, give the keys a shared hash tag such as {user-7} so they live in the same slot.
    How do you change a customer's limit at runtime?
    The bucket configuration is passed on every call, so it can come from a config service. The script clamps existing tokens to the new capacity, so lowering a limit takes effect immediately.
    Where would you still use an API gateway?
    For coarse, per-IP edge protection before traffic reaches your services. This library handles limits that need business context (per merchant, weighted operations) and traffic that never passes a gateway, like Kafka consumers.
    What breaks first at very large scale?
    A single hot key, because one key lives on one shard. The deny cache absorbs its rejected traffic; token leasing or splitting that tenant across sub-buckets handles its allowed traffic.
